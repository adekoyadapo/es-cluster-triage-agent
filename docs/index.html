Stack Monitoring

Start with the evidence layer Elastic already gives you

Stack Monitoring collects performance metrics and logs from Elasticsearch nodes, Kibana, Logstash, and Beats. Data is stored in dedicated monitoring indices and visualized in the Kibana Stack Monitoring UI. In Elastic Cloud Hosted, collection is automatic. For self-managed clusters, deploy Metricbeat with the Elasticsearch module or use internal collection.

What Stack Monitoring collects per node

Cluster healthgreen / yellow / red + reason
JVM heap & GCused %, old-gen GC count & duration
CPU & system loadprocess.cpu.pct, OS load average
Disk & filesystemfree space, read/write stats per node
Thread pool queueswrite, search, bulk rejections per pool
Shard allocation stateunassigned shards, recovery progress
Indexing & search ratedocs/s, query latency, shard segment counts
Why start here: Stack Monitoring turns a vague "something feels slow" report into a structured cluster view — before the agent adds any interpretation. The evidence must come first.
Best practice: ship monitoring data to a separate cluster so an outage does not eliminate your visibility into what caused it. See self-managed setup guide.

Skills — 1 of 2

Broad cluster health and resource pressure

Skills are the reusable troubleshooting units the agent invokes after reading monitoring data. The first two skills answer the broadest question: is this a cluster-wide issue or a resource bottleneck?

Skill 01 — Cluster Health

Elasticsearch Cluster Health Triage

Diagnoses red/yellow cluster status, node loss, heap pressure, CPU spikes, and broad instability. The first skill to invoke after any monitoring alert — it anchors whether the issue is cluster-wide or localized before narrowing further.

cluster_health_summary red_yellow_periods node_last_seen node_pressure_summary jvm_gc_pressure
ES docs: Cluster Health API · Node Stats API · JVM GC in node stats
Skill 02 — Resource Pressure

Elasticsearch Resource Pressure Triage

Converts "the cluster is slow" into a precise diagnosis: disk saturation, shard imbalance, write/search queue build-up, or thread pool rejections. Best invoked when monitoring shows latency or rejection spikes rather than cluster health changes.

disk_shard_pressure thread_pool_rejections node_pressure_summary
ES docs: Thread Pool Stats · Cat Shards API · Allocation Explain
Routing rule: always run Skill 01 first. If cluster health is green and the symptom is latency or rejections, move to Skill 02. The monitoring baseline query (slide 5) gives the agent enough data to pick the right skill without asking the user.

Tools & Queries — 1 of 2

Cluster baseline and health queries

Every triage session starts with a broad baseline read. These queries answer the first question fast: is the issue cluster-wide, node-specific, or already narrow enough for a focused skill?

workflow input

Stack monitoring baseline (ES|QL)

Runs once per triage session to orient the agent. Returns the highest-pressure nodes first.

FROM metrics-elasticsearch.node.stats-* | WHERE @timestamp >= NOW() - 1h | WHERE elasticsearch.cluster.name IS NOT NULL | STATS last_seen = MAX(@timestamp), avg_heap_pct = AVG(elasticsearch.node.stats.jvm.mem.heap.used.pct), max_heap_pct = MAX(elasticsearch.node.stats.jvm.mem.heap.used.pct), max_cpu_pct = MAX(elasticsearch.node.stats.process.cpu.pct), write_rejected = MAX(elasticsearch.node.stats.thread_pool.write.rejected.count), search_rejected = MAX(elasticsearch.node.stats.thread_pool.search.rejected.count) BY elasticsearch.cluster.name, elasticsearch.node.name | SORT max_heap_pct DESC | LIMIT 10
Points the agent to the most-pressured node before any skill runs. Source: Node Stats API
cluster_health_summary

Cluster health snapshot

Used by Skill 01. Checks cluster-wide status, node count changes, heap, CPU, and rejection totals over the last hour.

FROM metrics-elasticsearch.cluster.stats-* | WHERE @timestamp >= NOW() - 1h | STATS status = LAST(elasticsearch.cluster.stats.status), node_count = MAX(elasticsearch.cluster.stats.nodes.count.total) BY elasticsearch.cluster.name | SORT elasticsearch.cluster.name
Answers: is the cluster itself unhealthy, or is the investigation at node level? See Cluster Health docs.
jvm_gc_pressure

GC pressure detection

Used by Skill 01. Identifies nodes spending excessive time in garbage collection — a leading indicator of heap exhaustion.

FROM metrics-elasticsearch.node.stats-* | WHERE @timestamp >= NOW() - 30m | STATS gc_collection_time = MAX(elasticsearch.node.stats.jvm.gc.collectors.old.collection_time_in_millis) BY elasticsearch.node.name | WHERE gc_collection_time > 5000 | SORT gc_collection_time DESC
Tools & Queries — 2 of 2

Resource, index, lifecycle, and logs queries

These query families narrow a broad symptom into a specific resource, index, or policy answer. The agent selects the right family based on what the baseline query returned.

disk_shard_pressure & thread_pool_rejections

Resource pressure queries (Skills 01–02)

Separates "the cluster is slow" from infrastructure-level saturation.

-- disk pressure per node FROM metrics-elasticsearch.node.stats-* | WHERE @timestamp >= NOW() - 30m | STATS disk_used_pct = MAX(elasticsearch.node.stats.fs.total.available_in_bytes) / MAX(elasticsearch.node.stats.fs.total.total_in_bytes) * 100 BY elasticsearch.node.name | SORT disk_used_pct ASC
Ref: Cat Shards · Allocation Explain
hot_shards_analysis & slow_index_queries

Index pressure queries (Skill 03)

Finds the specific indices and shards generating most load.

FROM metrics-elasticsearch.index.stats-* | WHERE @timestamp >= NOW() - 15m | STATS indexing_rate = MAX(elasticsearch.index.stats.indexing.index_total), search_latency = MAX(elasticsearch.index.stats.search.query_time_in_millis) BY elasticsearch.index.name | SORT search_latency DESC | LIMIT 10
Ref: Index Stats API · Slow Log
ilm_stuck_indices & mapping_explosion_detection

Lifecycle queries (Skill 04)

Surfaces ILM stalls and runaway mapping growth before they cause data loss.

-- ILM stuck indices FROM .monitoring-es-* | WHERE @timestamp >= NOW() - 1h | WHERE elasticsearch.index.ilm.phase_time IS NOT NULL | STATS max_phase_time = MAX(elasticsearch.index.ilm.phase_time) BY elasticsearch.index.name, elasticsearch.index.ilm.phase | WHERE max_phase_time > 300000 -- >5 minutes | SORT max_phase_time DESC
Ref: Explain Lifecycle API · ILM overview
error_log_summary & audit_security_events

Logs and security queries (Skill 05)

Surfaces error patterns and auth failures when metrics are clean but symptoms persist.

FROM logs-elasticsearch.server-* | WHERE @timestamp >= NOW() - 1h | WHERE log.level IN ("ERROR", "WARN") | STATS error_count = COUNT(*) BY log.logger, message | SORT error_count DESC | LIMIT 20
Ref: Audit event types · Logging config
Agent Builder Setup

Package the triage behavior into a reusable agent

Agent Builder in Kibana is where the routing logic lives. Instead of re-prompting the same triage steps in every chat session, you define the agent once — attach skills, set response format, scope permissions — and the behavior stays consistent and reusable.

Setup sequence

1
Create the agent in Kibana

Define the cluster triage role, system prompt, and structured response format so downstream workflows can parse the output without guessing.

2
Attach skills and query tools

Connect all five skills and their 19 underlying ES|QL query tools. The agent selects the right skill based on the monitoring baseline output.

3
Align permissions with monitoring scope

Use the same Kibana space. Grant least-privilege read access to monitoring indices only — the agent should observe, not mutate cluster state.

4
Validate the routing

Test with known cluster states — yellow due to replica, red due to primary loss, high heap — to confirm the agent selects the correct skill each time.

Exposing Agents with MCP

MCP is the handoff layer to external clients

Once the agent is packaged in Agent Builder, enable the MCP server in Kibana and point any MCP-compatible client at the endpoint. The agent logic stays centralized — external clients just see a clean tool interface.

What MCP enables

Claude Desktop / Claude CodeDirect tool invocation from chat
Cursor / VS CodeInline triage during incident response
LangChain / LlamaIndexComposable triage tool in pipelines
Agent-to-Agent (A2A)Triage agent as a sub-agent for orchestrators
Core benefit: one MCP endpoint, all clients — no rebuilding the logic outside Kibana.

{ "mcpServers": { "elastic-cluster-triage": { "command": "npx", "args": ["-y", "@elastic/mcp-server-kibana"], "env": { "KIBANA_URL": "https://<your-kibana-host>", "KIBANA_API_KEY": "<base64-encoded-id:api_key>" } } } }

Generates a Kibana API key under Stack Management → API Keys. Scope to read-only on monitoring indices for least privilege.

Agent Builder MCP endpoint — SSE transport

Generic SSE client (Cursor, LangChain, etc.)

{ "mcpServers": { "elastic-cluster-triage": { "url": "https://<kibana-host>/api/agents/<agent-id>/mcp", "headers": { "Authorization": "ApiKey <base64-encoded-id:api_key>", "kbn-xsrf": "true", "Content-Type": "application/json" } } } }

agent-id is found in Agent Builder → agent detail page URL. The SSE endpoint streams tool results back as the agent runs each skill query.

Claude Desktop Extension

Rich inline visualizations — packaged as a .mcpb extension

The triage agent ships as a self-contained .mcpb bundle: 22 diagnostic tools and 5 Kibana-style HTML panels that render directly inside Claude Desktop. No browser tab. No separate server.

One-command build & install

bash scripts/build-mcpb.sh # → elastic-cluster-triage-agent.mcpb (~16 MB) # Double-click → installs in Claude Desktop
Diagnostic tools22 (19 triage + 3 timeline)
Inline HTML views5 self-contained panels
Transportstdio — local, no network config
Build stackTypeScript · Vite · esbuild · mcpb
manifest.json — user_config fields

Prompted at install time

{ "elasticsearch_url": "https://<es-host>:9200", "elasticsearch_api_key": "<base64-id:key>", "kibana_url": "https://<kb-host>:5601", "kibana_api_key": "<base64-id:key>" }

Kibana fields are optional — required only for Kibana REST calls. ES API key scoped read-only to .monitoring-es-* is sufficient for all triage tools.

What renders inline in Claude Desktop

📈 Area Charts
Heap %, CPU, store-size growth with threshold lines & multi-series
⏱ Gauges
Kibana-style circular arc: heap %, disk %, CPU at a glance
📊 Histograms
GC time, rejection counts, error frequency as bar distributions
🔵 Scatter Plots
Indexing ops vs latency, docs vs store size — outlier detection
🟩 Status Heatmap
Lens-style timeline: green / yellow / red cells per 5-min bucket
↗ Investigation Actions
Drill-down buttons re-invoke Claude with the next diagnostic prompt

Data flow inside the bundle

ES|QL query → JSON payload → React + SVG → mcp-app.html → Claude iframe

Each view is a ~210 KB self-contained HTML compiled by Vite + vite-plugin-singlefile — zero external requests, fully offline. The React component picks the correct chart from a tool discriminator on the JSON payload. registerAppTool links each tool to its view.

Optional Agent

Application Index Triage — drill into a specific index or data stream

A second optional agent persona (app-index-triage-agent) deployed alongside the cluster agent. Use it when a symptom or alert names a specific index or data stream — the cluster agent answers at the wrong altitude for per-index problems. It reuses the same monitoring and log datastreams; no extra credentials or patterns needed.
